One process

The backend is one Spring Boot application with four modules, so module to module is a method call, not an HTTP call. There is no service token to leak and no assertion to forge.

Bytes go direct

Storage to phone over a short-lived signed URL, so a 6 MB book never occupies one of our request threads.

The key is wrapped

We hand out a book key wrapped to the reader's public key, so nobody in the middle can read the book, including flambeau.

02Three kinds of book

The access tier is set on the item by an operator. It is what makes the three flows differ.

Open access

Free to everyone. Creative Commons or similar.

Plaintext. No key, no licence, no borrow.

Read online or download. Keep it forever.

Subscription

The institution pays for a package.

Encrypted. Unlimited readers at once, so no copy counting.

Read online or download. Expires at the due date.

Elite

Premium, sold with a copy limit.

Encrypted. Borrow consumes one of N copies. Queue when they run out.

Online only. No download.

Why open access is not encrypted

An anonymous reader with no account must be able to open the book, because that is what open access means. So we would have to hand the key to anyone who asks, and a key given to anyone protects nothing. Plaintext also lets the reader pass the URL to a native viewer, which is close to zero code. We still use a short-lived signed URL, not for secrecy but to stop hotlinking and to keep usage logging.

Why Elite has no offline copy

An offline copy means the phone holds the ciphertext and a working key for as long as the licence lasts, and expiry is then enforced by the app, which the user controls. For two-copy premium content that trade is not worth taking. Elite fetches the ciphertext into memory, decrypts, renders and discards. The lock is simply that we stop issuing the next licence, which needs no cooperation from the device.

Say this at the showcase. Read offline is one of the seven capabilities and Elite visibly does not do it. That is a deliberate trade, not an oversight.

One process means the boundary is a convention, so make it a test

Across HTTP, one team physically could not reach another's collections. In one Spring context, @Autowired CatalogueItemRepository compiles from any package and Spring wires it happily. Two mechanical fixes, both in Week 1, both about two hours:

1. Implementations are package private in internal/, interfaces are public in api/. The shortcut then does not compile, which beats detecting it.
2. An ArchUnit test in CI forbidding cross-module repository access and any import outside an api/ package.

Catalogue search has to be server-side, because results are filtered by what the institution is entitled to. Searching on the client would mean shipping the whole catalogue to the phone and reimplementing entitlement rules there, and a member must never see a result they cannot open. So: we filter, you render.

It searches metadata, meaning title, authors, subjects and description. It does not search the text inside books. Worth reflecting in the UI copy, so a reviewer typing a phrase from page 88 does not report a bug.

Filtering

Filters are query parameters on the endpoints you already call, because filtering has to happen before pagination. Filter within a page of twenty and you show three results while the pager still says page 1 of 12.

Four rules for the client

  1. Follow hrefs, do not build URLs. The only construction you should ever do is expanding the templated search link, ".../search{?query}".
  2. Paginate by following the next link until it is absent. Do not count pages.
  3. An empty result is not an empty array. The OPDS schema forbids empty arrays, so a zero-result search returns a feed with a navigation entry pointing back at the catalogue. Render it as a browse-instead button, do not treat the missing publications key as an error.
  4. The acquisition link decides the buttons, not your own logic. rel=open-access means Read and Download. rel=borrow plus canPersist:false means Borrow with no Download. If we do not send a link, the button does not exist.

Two things that are yours to hold, not ours

Device fingerprints. A record of which devices a person has used is keyed by user, and users are yours. Our grant result returns keyFingerprint, the SHA-256 of the device public key that was sent; record it if you want a device registry. We log it in our own audit trail and nothing more.

The device public key must pass through untouched. You receive it from the app and hand it to our method unchanged. If you substituted your own key you would receive a book key wrapped to yours, and could read every title. The reader detects this by comparing the returned keyFingerprint against the hash of its own public key, so the pass-through is verifiable rather than merely trusted.

Reading a file, in five lines

1  bek       = RSA-OAEP-256-decrypt(devicePrivateKey, encryption.wrappedBek)
2  bytes     = GET content.url                  whole object, Range-resumable
3  nonce     = bytes[0 .. 11]
4  plaintext = AES-256-GCM-decrypt(bytes[12 ..], bek, nonce)   tag verified here
5  hand plaintext to the PDF, EPUB or audio renderer

the index is identical: its own nonce in its own first 12 bytes, same key
open access and ALL audio: encryption is null, the URL is a plain file

Step 5 is the point of the design. Native PDF and EPUB renderers on both platforms want a file or a complete buffer, so you hand them decrypted bytes and they behave normally. Section 10 has the full reasoning and the three read paths.

Three rules that are not negotiable

1. Never write plaintext to disk, for any tier. Subscription stores the ciphertext as received; Elite stores nothing at all.
2. Never decrypt a partial object. The authentication tag covers the whole ciphertext, so a partial buffer cannot be verified. Wait for the full download, then decrypt once.
3. A failed tag must fail loudly. Tampered or truncated. Show an error, never render whatever came out. That is the entire reason for choosing an authenticated cipher.

What you do not have to build

No chunk layer, no range-to-chunk translation, no offset arithmetic, no cache of decrypted pieces, no resume at a piece boundary, and no lazy byte-source adapter into the renderer. Whole-file encryption removes all of it. Section 10 explains why we made that choice and what it costs.

07Ingest and encryption

Subscription and Elite are encrypted as one whole file. Open access and all audio are stored as-is.

The object layout

Every encrypted object, content and index alike, has the same three-part shape. The nonce travels with the ciphertext, so nothing has to be derived and nothing has to be agreed beyond the first twelve bytes being the nonce.

content.enc
┌────────────────┬──────────────────────────────────────────┬──────────┐
│ nonce 12 bytes │ ciphertext, same length as the plaintext │ tag 16 B │
└────────────────┴──────────────────────────────────────────┴──────────┘
  random per                                                  authentication
  object

cipherLength = 12 + originalLength + 16

index.enc       identical layout, same book key, DIFFERENT random nonce
Why two independent random nonces

The content object and the index object are encrypted under the same book key. If both derived their nonce from a counter, both would start at zero, and the same key with the same nonce over two different plaintexts is a total break in AES-GCM: it leaks the XOR of the plaintexts and it leaks the authentication subkey, which lets an attacker forge valid tags for the whole book. Both plaintexts begin with predictable bytes, a PDF header and a JSON header, so it would be directly exploitable.

Two independent random 12-byte nonces, each stored inline, make that structurally impossible rather than something a test has to catch. There is no derivation rule, no byte order to agree, and nothing that fails silently.

The pipeline

 1  contentState = QUEUED, then ENCRYPTING
 2  if accessTier == OPEN_ACCESS or contentType == AUDIO:
        PUT the file as-is, no key, no encryption block
        skip to step 7
 3  bek = SecureRandom(32)     ALWAYS fresh. never read an existing wrappedBek
 4  nonce = SecureRandom(12)
    PUT nonce || AES-256-GCM(plaintext, bek, nonce) → storageKey
 5  try {                                                       non-fatal
        text       = TextExtractor.extract(plaintext)   PDFBox or epublib
        index      = IndexBuilder.build(text)
        indexNonce = SecureRandom(12)                   its OWN nonce
        PUT indexNonce || AES-256-GCM(index, bek, indexNonce) → indexKey
        hasSearchIndex = true
    } catch (Exception e) {
        hasSearchIndex  = false

Why this shape

  • One key per book so a leaked key exposes one title, not the library.
  • Wrapped by a master key so a stolen database dump is useless without it.
  • Stored apart from the book so a stolen storage bucket is useless too.
  • Rewrapped per reader so the same ciphertext serves everyone, and only that device can open its copy of the key.
  • Rotatable because the item records which master key wrapped it, so changing the master key rewraps 400 bytes per book rather than re-encrypting 6 MB.
Be precise about two things

RSA direction. We encrypt with the public key, the phone decrypts with its private key. It is safe to accept a public key in a request precisely because possession of the private key is what grants access.

We never verify that possession. Anyone can send any device public key, so this binds a keypair, not a device. We have chosen not to add a possession proof for the prototype, so do not describe it as device binding. The field is called keyFingerprint, not deviceId, for that reason.

The index stores pages, never byte positions

A PDF is a compressed container. The text of page 88 is not at file byte 2,000,000 and no formula turns one into the other, because only a PDF parser can answer where page 88 is. So the index stops at the page. Turning a page into a rendered view is the reader engine's job, and it already knows how.

One key unlocks both, and that is deliberate

The index contains the book's words, so an unencrypted index is a searchable copy of the book. An index under a different key would let a device search a book it is not licensed to read. One key, one thing to wrap, one thing to destroy at expiry. Open access is the exception: the book is plaintext, so its index is too.

10How reading works

Why there is no chunking, what that costs, and exactly what the reader does instead.

The choice

An earlier version cut every encrypted book into fixed 64 KB pieces and encrypted each separately, so piece 30 could be opened without touching pieces 0 to 29. It buys real seeking. It also buys a great deal of machinery on both sides, and it is where the nonce collision came from.

Two things that look redundant and are not

Step 3 re-resolves the entitlement even though flambeau called check() a moment earlier. In one process that looks wasteful. It is the invariant that makes the interface safe to expose: a future caller who forgets step one cannot obtain a key. The resolver is cache-backed, so it costs microseconds.

LoanProof needs no signature. Across HTTP we would have to trust a JSON assertion we could not verify. In-process, flambeau constructs the object itself immediately after reading its own repository and hands it to our method. There is no wire, so there is nothing to forge. Keeping it a distinct type rather than two loose strings is what documents the trust boundary for whoever reads this in Week 7.

There is no third seam

We do not call flambeau while building a feed. That would make our module depend on theirs, which makes the dependency circular and kills the splittable-later property the brief asks for. The app calls GET /api/v1/availability?itemId= on the detail screen instead: one book, one call, at the moment the user is deciding. Our module compiles with no knowledge that flambeau exists.

On expiry with no return, the lease TTL frees the copy on its own. There is no offline file to lock, so the lock is simply that we stop issuing the next licence.

Honest caveat

canPersist: false is enforced by the reader. A modified client could keep the bytes it has fetched. The one-hour licence is what actually bounds the exposure, and that is true of all DRM.

16Known limits

This is a prototype. These are deliberate, and saying them plainly at the showcase reads as engineering judgement rather than oversight.

LimitWhy we accepted itWhat production would do
The device public key is not proven. A stolen session can be read on a laptopA possession proof does not stop a rooted device anyway, so we reworded rather than builtSign the request with the private key and verify before wrapping
A leaked book key cannot be revoked. That title stays readable foreverTrue of all offline DRM. Re-encryption does not reach copies already on devicesPer-session key derivation, so a dumped key expires with the session
Offline expiry is client-enforcedThe device holds a key that works. Signing the licence raises the bar from editing JSON to patching a binaryHardware attestation and mandatory check-in
Encrypted files are decrypted whole, so there is no render-before-downloadA 6 MB PDF is about 2 seconds on wifi, and chunking would have cost two teams several daysChunked encryption with per-piece tags and a piece table
Audio is not encryptedWhole-file encryption cannot seek, and scrubbing is required behaviour. The URL still expires in minutesChunked encryption, or per-segment keys as streaming formats do
Master key lives in config, not a managed key serviceNo key management service in the prototype environmentKMS or Vault with automatic rotation
Four clocks decide access and time sync is assumed, not enforcedDocumentation is the cheap mitigation. The reader keeps an hour of grace before deleting a keyEnforced time sync and server-time headers
No rate limit on content accessPrototype traffic, and repeat calls are cheap because the resolver is cachedPer-user and per-IP limits, plus a wrapped-key cache for the URL lifetime
Elite needs the network every 20 minutesThe trade for having no offline copy of premium contentLonger licences with a revocation check
What this design does achieve

Content is encrypted at rest. The key is never transmitted in the clear and is never visible to flambeau, team1 or the storage provider. A stolen bucket dump is useless without the master key, and a leaked signed URL yields ciphertext only. Offline reading works with no network. Entitlement is resolved from the database on every request, never from a token claim, so revocation takes effect on the next request rather than at token expiry.
